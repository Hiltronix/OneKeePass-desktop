## Hardening implemented during final source review

**PAG-01 — Unsafe byte-buffer reinterpretation in Windows Pageant SID verification**

`src-tauri/src/ssh_agent/pageant.rs` previously converted `Vec<u8>::as_ptr()` to `*const TOKEN_USER` and dereferenced that pointer as a Rust reference. Although Windows/x86 typically aligns the allocation, `Vec<u8>` only guarantees alignment for `u8`, so such a reference is not formally valid for `TOKEN_USER` in all cases. The code now ensures the returned buffer has at least `size_of::<TOKEN_USER>()` bytes and uses `std::ptr::read_unaligned` to obtain the structure safely; it denies null owner/user SID values. Debug logging now records the comparison result without the actual user SID strings. This is a narrow memory-safety and privacy correction; Pageant protocol, key lifetime and approval settings remain unchanged.

## Remaining findings classified by needed action

**Architecture/design — partially remediated:** The two **unexposed plaintext XML export** handlers and frontend invoke wrappers were removed with user approval in revision 2026-10-27-17. This closes that particular IPC write path without removing a visible user workflow. Other file import and save operations still take renderer-provided paths. Robustly restricting those requires a native file-picker broker or equivalent user-authorization mechanism; the privileged webview is currently entrusted with results. No changes to normal KDBX Save/Save As, attachment operations or CSV imports were made.

**Dependency engineering:** The five Rust advisories require individual root-cause/dependency-chain analysis and tested upgrades or mitigations; neither a routine lockfile bump nor ignoring known CVEs is an adequate blanket remedy.

**OS-level security and verification:** Deny/permit decisions in the Windows firewall, the effective local process network behavior, Windows credential/clipboard history, account separation, WebView2 host-installed behavior and file ACL inheritance cannot be established by static source inspection alone.

**Lower-priority privacy questions:** Windows clipboard-history exclusion, Pageant log retention and native WebView2 password-autosave policy can be tightened in a future, separately tested change without conflating them with removal of Rust dependencies.

## Minimum Windows acceptance checklist (disposable data)

1. Re-run the read-only `scripts/Audit-WindowsSecurity.ps1` to capture the live named-pipe ACL, filesystem ACLs and related processes. **Do not treat TCP samples as exhaustive traffic monitoring.**
2. WFP/ETW network trace: process-attributed DNS/UDP/short TCP while launching, unlocking, copying, saving, locking, SSH-agent on/off, entering a search query, and quitting.
3. Cross-account SSH-agent test: from a different non-administrator Windows account, verify identity enumeration/signing fail against `\\.\pipe\openssh-ssh-agent`; verify expected user succeeds with disposable ED25519 and RSA keys, both through OpenSSH and Pageant-compatible KiTTY/WinSCP.
4. ProcMon + filesystem checks: confirm cache/attachment file creation under portable `temp`, post-exit cleanup leaves `temp` empty and `onekeepass-data` intact. Repeat with an external viewer holding a decrypted file open, forced process termination, and rapid restart.
5. Inspect ACLs on `onekeepass-data`, backups, logs and `temp` on the actual NTFS volume; verify no unprivileged account can access decrypted viewer files while open.
6. Exercise file import/export using disposable data: CSV, encrypted KDBX save/save-as, icon and SSH-key import, and **plaintext XML export** to an explicitly selected destination; confirm no unrequested overwrite.
7. Verify Windows clipboard timeout and inspect the Windows Clipboard History setting separately. Ensure intentionally saved passwords do not remain in history if history is enabled.

**Review classification:** The outstanding *source-review* work is complete. The overall **security audit is NOT closed** until the design decisions about renderer filesystem access and advisories are resolved or explicitly accepted, and the listed Windows runtime observations are recorded.


### Quick-XML review resolution — revision 2026-10-27-18

The original assessment must distinguish XML code actually linked to OneKeePass from lockfile entries for other platforms. The pinned `onekeepass-core` has used `quick-xml 0.41.0` for normal encrypted KDBX XML parsing/writing, in-memory locking serialization and version 2 XML keyfile handling; this is active functionality. The older `quick-xml 0.39.4` instance was used **only** by Linux `wayland-scanner 0.31.10`, via Tauri clipboard manager → arboard → wl-clipboard-rs → wayland-client, for generating Wayland protocol APIs. It was not the core KDBX XML parser, nor a Windows runtime dependency.

Remediation updates the locked `wayland-scanner` to patch release **0.31.11** (published with `quick-xml ^0.41`), reusing the existing `quick-xml 0.41.0`, and removes the redundant old lock entry. Core source code is unchanged; the core already handles the 0.40+ `read_text` API change. Cargo `--locked` resolution, Windows CI, the post-change RustSec scan and Linux compatibility must be verified. RSA/crypto-bigint not touched in this revision.
